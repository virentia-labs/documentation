# Владение полями и статические модели

Эти модельные API требуют `@virentia/core` версии 0.11.2 или новее.

Объявляйте определение поля один раз, а для каждой формы создавайте собственного
ребёнка этого определения. Две формы с определением `Email` получают одинаковое
поведение и независимые значения. Когда им нужен один существующий экземпляр
поля, подключайте его через `refs`.

## Определения и собственное поведение

Модельные фабрики импортируются из `@virentia/forms/models`:

<<< @/examples/packages/forms.ts#definitions

`fieldModel` хранит значение, метаданные, фокус, ошибки и состояние сброса в
traits. `staticModel.setup` объявляет общий граф юнитов один раз; создание
экземпляров не объявляет новые юниты полей. Нативный `createField` остаётся доступен.

Дополнительные методы существующего `fieldType` можно перенести в модель.
Используйте `createField` или `base` расширения, чтобы методы работали с
trait-ячейками модели:

<<< @/examples/packages/forms.ts#custom

Нормализованное конструктором начальное значение, метаданные и исходная ошибка
фабрики становятся defaults поля. Явное значение DTO имеет приоритет.
Восстановленный scope snapshot сохраняет свои метаданные и исходное состояние reset:

<<< @/examples/packages/forms.ts#defaults

`create` выполняется при объявлении общего графа определения. Он не вызывается
заново для каждого DTO или `fill`; при необходимости нормализуйте последующий
ввод методами поля или преобразованием входных данных модели.

## Массивы и объекты

Из определений можно собрать вложенные поля:

<<< @/examples/packages/forms.ts#collections

| Фабрика | Значение | Где задаётся поведение |
| --- | --- | --- |
| `fieldModel(initial, options)` | Одно значение | `validate`, метаданные и необязательный `create` |
| `arrayFieldModel(initial, options)` | Упорядоченный массив | Определение `item`; при его отсутствии создаётся scalar-определение |
| `shapeFieldModel(schema, options)` | Объект | Определения или начальные значения по ключам; `additional` для новых ключей |

В `.field` массивов и объектов сохранены `fill`, `reset`, валидация и методы
изменения состава. `.value` модели — readonly-производный стор: изменяйте его
через API поля или writable-значение scalar-ребёнка.

Новые элементы из обычных значений становятся принадлежащими коллекции
`children`. Передача существующего модельного поля в `push`, `add` или `replace`
подключает его через `refs`; lifetime остаётся у исходного владельца.
Определение такого поля должно быть объявлено через `item`, схему shape или
`additional`. Поле из другого application scope будет отклонено.

Удаление своего элемента ожидает disposal, включая асинхронный cleanup. Удаление
заимствованного элемента освобождает ref. `move`/`swap` сохраняют экземпляры.
`reset` восстанавливает исходный состав и значения. Поведение нативных
`createArrayField` и `createShapeField` сохранено.

Перекрывающиеся изменения не удаляют уже удаляемого ребёнка повторно. Каждая
операция ожидает cleanup, который запускает сама; `reset` дожидается текущих
удалений до восстановления baseline, чтобы не создавать прежний ID во время disposal.

## Форма владеет полями

Разрешайте схему в `setup`, а отсутствующих детей создавайте в синхронном
`onCreate`. Проверки наличия сохраняют детей, уже восстановленных из DTO:

<<< @/examples/packages/forms.ts#form

Вызывайте `.create()` в scope приложения или создавайте модель через `children`
родителя. Привязанная форма, вложенные сторы и методы полей доступны напрямую:

<<< @/examples/packages/forms.ts#edit

`form.pick(...)`, `createWizard` и `createWizardForm` тоже объявляются в `setup`.
Проекции, текущая форма и формы шагов визарда сохраняют привязку к экземпляру.
React `useField`/`useForm`/`useWizardForm`, Zod-валидаторы, Vue `useUnit` и
Effector lenses принимают эти привязанные API.

Валидация формы считает заменённый запуск и abort при disposal вызывающей
модели отменой. Ошибка самого валидатора по-прежнему отклоняет явно ожидаемый
`form.validate()`; обработка отмены её не скрывает.

## Переиспользовать определение или разделить экземпляр

`children.one(Email)` в двух моделях создаёт независимые поля почты. Для общего
черновика оставьте одного владельца, а редакторы подключите к нему:

<<< @/examples/packages/forms.ts#sharing

Disposal редактора оставляет email профиля живым. При `nullify` удаление поля
владельцем очищает refs. Схема, которой нужен этот ref, должна использоваться
только пока он существует: закройте редактор или обработайте отсутствие поля.

`.static()` создаёт отдельный модульный граф. Используйте его для намеренно
общего модульного lifetime. Обычным полям формы нужны `.create()`/`children`,
а разделяемому существующему экземпляру — `refs`; `.static()` для этого не нужен.

## Передача JSON и hydration

Используйте стабильные имена/SID моделей и явные стабильные ID корней.
`json()` передаёт DTO принадлежащих детей, состав и порядок. Вместе с ним
передавайте scope snapshot для сохранения исходного состояния reset, метаданных
и ошибок:

<<< @/examples/packages/forms.ts#restore

Восстановите scope и корневые модели до hydration UI. На сервере и клиенте
используйте одинаковое представление и UI `identifierPrefix`; тогда UI
подключится к серверному DOM. `onCreate` не должен перезаписывать восстановленных
детей. Каждому запросу и клиентскому приложению нужен собственный scope.

В списках нативного UI `.field.items` — стор массива. Замена этого массива
пересоздаёт строки `For` по существующему контракту UI; стабильные экземпляры
полей не означают DOM reconciliation. Сама hydration использует совпадающие
серверные узлы.

Заимствованные поля передаются ссылками, а не вложенными DTO владения:
передайте DTO их владельца и восстановите его перед заимствующими моделями.
Общее определение не делает экземпляры или значения глобальными.
