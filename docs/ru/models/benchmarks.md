# Бенчмарки моделей

Здесь приведены сохранённые замеры из презентации Virentia. Во всех сценариях используется Core из commit [`e5743a8`](https://github.com/virentia-labs/virentia/tree/e5743a89e4cb8b9cdad41f2d7bc1f78714fc8c81). Создание и память измерены 14 сентября 2026 года, поиск — отдельно 20 октября 2026 года по UTC. Внутри каждого сравнения оба варианта запускались в одинаковой среде.

## Что разделяет `staticModel`

`staticModel` создаёт юниты и связи один раз при объявлении. Каждый экземпляр хранит собственные значения полей в своём scope, а вызов события экземпляра работает именно с его данными. Это позволяет не строить одинаковый граф заново для каждой строки, элемента списка или блока. Если экземпляру нужны свои замыкания или динамически создаваемые юниты, используй `model`. API и различия описаны в [руководстве по видам моделей](./kinds).

## Создание и память 10 000 экземпляров

Исходная серия выполнена на **Apple M3 Pro, 36 GiB RAM, Node 22.15.0, V8 12.4.254.21-node.24, macOS/Darwin 25.6.0, arm64**. Эта среда указана в методике бенчмарка из презентации.

Оба варианта объявляют три поля (`count`, `title`, `active`), событие, реакцию с увеличением `count` и computed `doubled`. Каждый экземпляр получает одно awaited-событие, затем читается его computed. В этом сценарии нет индексов, UI-подписчиков и сетевых операций.

| Метрика | `model` | `staticModel` |
| --- | ---: | ---: |
| Определение, измерено отдельно | 0,0378 мс | 0,2485 мс |
| Создание 10 000 экземпляров | 345,03 мс | 57,49 мс |
| Одно событие на экземпляр | 61,29 мс | 48,03 мс |
| Dispose 10 000 экземпляров | 268,88 мс | 251,24 мс |
| Прирост heap активной коллекции | 199,57 MiB | 46,96 MiB |

В таблице показаны медианы **пяти свежих процессов Node для каждого варианта**. Внутри каждого процесса есть прогрев на 100 экземплярах того же вида, порядок вариантов чередуется. `createMs` измеряет только цикл `collection.add`; объявление определения измеряется отдельно. Отношение неокруглённых медиан времени создания составляет примерно **6,00×**.

Память — это прирост `process.memoryUsage().heapUsed` относительно baseline после обновлений, первого чтения computed, завершения микрозадач и пяти вызовов `global.gc()`. Один MiB равен 1 048 576 байтам. Сокращение примерно на **76,5%** включает определения, коллекцию, данные экземпляров, объекты runtime и кеши, которые удерживает этот снимок реализации. Это не оценка размера одних только полей экземпляра и не RSS.

Узлы считались в отдельных инструментированных процессах, исключённых из медиан времени и heap. Для 10 000 экземпляров получено **70 000 узлов модели у `model` и 7 общих узлов определения у `staticModel`**, плюс одна нода коллекции в обоих вариантах. Harness проверяет точную контрольную сумму computed и пустую коллекцию после dispose.

В этом commit сохраняются сильные registry узлов и scopes, а пул static scopes удерживает до 1 024 записей. Эти расходы входят в сохранённые результаты. Время dispose не включает последующий GC, а сам dispose не означает полного освобождения heap.

## Поиск экземпляра по полю

Это отдельное сравнение **двух способов поиска по одним и тем же индексированным экземплярам `staticModel`**. Оно не сравнивает `model` со `staticModel`.

Среда поиска: **Apple M1 Max, Node 24.14.0, V8 13.6.233.17-node.41, macOS/Darwin 25.5.0, arm64**, esbuild 0.21.5 и TypeBox 0.34.52. Runner извлекает Core через `git archive` из зафиксированного commit, поэтому незакоммиченные изменения в измерение не попадают.

Создаются 10 000 экземпляров Point с уникальными значениями `x` и детерминированно перемешанным порядком вставки. Каждый процесс выполняет 1 000 успешных поисков, меняя `x` при каждом вызове:

```ts
// Запрос использует уже заполненный eq-индекс.
collection(Point).where(Point.x.eq(x)).first;

// Цикл читает те же instance facade и возвращает первое совпадение.
for (const row of rows) {
  if (row.x.value === x) return row;
}
```

| Метод | Медиана времени всех 1 000 поисков |
| --- | ---: |
| Перебор | 2135,86 мс |
| Запрос с eq-индексом | 182,42 мс |

Оба способа прогреты, порядок измерения чередуется в пяти независимых процессах. Отношение медиан составляет примерно **11,71×**. Цепочка дескрипторов запроса строится заново при каждом поиске, а меняющийся критерий исключает попадания в однослотовый кеш результата. Точное совпадение возвращённых экземпляров и промахи проверяются вне измеряемого цикла.

Таймер включает построение дескриптора, выполнение запроса и потребление результата. Объявление, создание экземпляров, заполнение индекса, проверки и прогрев исключены. Записей в коллекцию в измеряемом цикле нет, поэтому поддержание индекса при обновлениях здесь не измеряется. В этой реализации eq-путь дополнительно фильтрует `state.order` по hash bucket; результат не гарантирует O(1) для всего запроса или такое же ускорение приложения целиком.

## Как повторить измерение

Сохрани каждый runner рядом с соответствующим harness:

- <a :href="withBase('/benchmarks/run-virentia-models.mjs')">Runner моделей</a> и <a :href="withBase('/benchmarks/virentia-models.harness.ts')">harness моделей</a>.
- <a :href="withBase('/benchmarks/run-virentia-query-search.mjs')">Runner поиска</a> и <a :href="withBase('/benchmarks/virentia-query-search.harness.ts')">harness поиска</a>.

Подготовь отдельный checkout с зафиксированными исходниками и зависимостями:

```sh
git clone https://github.com/virentia-labs/virentia.git virentia-benchmark
git -C virentia-benchmark checkout e5743a89e4cb8b9cdad41f2d7bc1f78714fc8c81
pnpm --dir virentia-benchmark install --filter @virentia/mutable... --ignore-scripts --frozen-lockfile
```

В Node 22.15.0 запусти runner моделей из каталога со скачанными файлами:

```sh
node run-virentia-models.mjs /absolute/path/to/virentia-benchmark models-results.json
```

Для поиска используй Node 24.14.0:

```sh
node run-virentia-query-search.mjs /absolute/path/to/virentia-benchmark lookup-results.json
```

Runner моделей использует текущий HEAD checkout, поэтому перед запуском проверь commit и отсутствие tracked changes. Runner поиска извлекает зафиксированный Core самостоятельно. При интерпретации нового запуска учитывай записанные версию runtime и оборудование; сравнивай варианты внутри сценария, не объединяя времена с разных машин.
