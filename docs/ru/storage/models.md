# Storage в статических моделях

Эти модельные API требуют `@virentia/core` версии 0.11.2 или новее.

Объявляйте граф модели один раз, а storage подключайте каждому живому экземпляру
из привязанного метода или `onCreate`. `setup` объявляет общий граф; открытая в
нём связь storage привяжет runtime-ресурс к этапу объявления определения.

<<< @/examples/packages/storage.ts#model

В `source` передаётся writable data-поле или `.value` scalar-модели поля,
включая собственного ребёнка или поле по ref. Привязанный источник сохраняет
свой scope. Cleanup принадлежит экземпляру, вызвавшему `persist`; заимствование
источника не передаёт его lifetime. `.value` array/shape является производным
стором и не подходит как writable-источник. При необходимости сохраняйте их
DTO/snapshot явно.

## Отдельные ключи и cleanup

Для независимых сохранённых значений используйте разные боксы или ключи.
`persist` возвращает явный `stop()` и регистрирует cleanup у вызывающей модели:

<<< @/examples/packages/storage.ts#use

В `local()` и `session()` одинаковый ключ намеренно обращается к одной записи
браузерного хранилища. Изоляция scope не меняет внешний ключ. Явные группы
`owner` остаются полезны для независимо заменяемых подписок.

## SSR и hydration

Каждому серверному запросу нужен свой scope. Восстановите DTO моделей и scope
snapshot до подключения клиентского storage. Существующая запись хранилища
заполняет writable-источник; при её отсутствии источник заполняет бокс.
Определите, должны ли клиентские настройки заменять серверное значение.
Подключайте их после DOM hydration, если начальный DOM должен совпадать с серверным.

О боксах, сериализации и двусторонней связи — в [persist](./persist).
О `children`/`refs` и передаче JSON — в [модельных полях формы](/ru/forms/models).
