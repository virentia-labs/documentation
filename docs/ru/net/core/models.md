# Запросы в статических моделях

Эти модельные API требуют `@virentia/core` версии 0.11.2 или новее.

Объявляйте query, mutation и общие триггеры в `staticModel.setup`. Возвращайте
нативный API напрямую: `.create()` привязывает вызов и вложенные data/lifecycle
юниты к экземпляру. Дополнительные aliases для `load.data` не нужны.

сохраняют параметры, типы результата и существующие операторы.

## Независимые запросы

<<< @/examples/packages/net.ts#use

Экземпляры разделяют объявления, сохраняя независимые `data`, `pending`,
последние параметры, refresh/reset и отмену. Disposal экземпляра отменяет его
запросы и освобождает триггеры. Соседние экземпляры продолжают работать.
Для заменяемого runtime-триггера сохраняйте disposer, возвращаемый `trigger`.

Объявляйте триггер один раз в `setup`. Создавайте его заново при вызове
привязанного метода только когда нужен более короткий lifetime. `.static()`
создаёт отдельный модульный граф и нужен именно при таком выборе владения.

## Async-контекст и SSR

Каждому SSR-запросу нужен свой scope. Завершите запросы сервера, передайте DTO
моделей и состояние scope, восстановите их до рендера/hydration клиента.
Незавершённые запросы и abort controllers — runtime-ресурсы: при необходимости
создавайте их заново, а не передавайте как сериализованные данные.

Прямой `await` юнита Virentia переносит его async-контекст. После обычного
внешнего Promise, таймера или `fetch` вызывайте следующие юниты и обращайтесь к
непривязанным сторам через захваченный `scoped` runner. В валидаторах форм
читайте значения после внешнего ожидания через `ctx.read`. Привязанные API
модели сохраняют свой экземпляр.

См. [query](./query), [mutation](./mutation), [триггеры](./triggers) и
[владение полями формы](/ru/forms/models). Нативные API уровня модуля остаются
доступны для намеренно общего графа приложения.
